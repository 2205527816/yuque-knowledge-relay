# 处理流程与状态设计

本文说明一篇文章从进入系统到写回语雀的全过程，以及它在数据库里的状态变化。排错时对照本文的「状态」和「阶段」两张表最快。

## 1. 总览

```
导入 → 入队 → 分类 → 建档 → 抽词 → 释义 → 待审核 → 审核 → 写回
```

其中「导入到待审核」由后台单工队列自动完成，「审核到写回」由人工触发。

系统同时维护三组互不干扰的状态：

| 状态组 | 字段 | 含义 |
|---|---|---|
| 处理状态 | `documents.status` | 流水线走到哪一步 |
| 阶段进度 | `documents.stage` / `stage_pct` / `stage_detail` | 当前处理中任务的细粒度进度 |
| 保留状态 | `documents.retention_status` | 是否仍在工作列表中出现 |

## 2. 处理状态

| 状态 | 中文 | 何时进入 | 下一步 |
|---|---|---|---|
| `imported` | 已导入 | 解析成功并写入数据库 | 等待分类 |
| `classified` | 已分类 | AI 打分完成且胜出且唯一 | 在语雀建档 |
| `pending_class` | 待归类 | 最高分低于阈值、或最高分并列、或打分结果两次校验失败 | 等人工在页面改分类 |
| `created` | 已入语雀 | 目标库建档成功，拿到文档 ID | 抽词释义 |
| `terms_ready` | 待审核 | 全部注释词释义生成完毕并一次性入库 | 等人工审核 |
| `written` | 已写回 | 带注释的正文成功写入语雀 | 可继续改词再写 |
| `failed` | 失败 | 任一环节报错且重试无效、任务超时、或服务重启时任务中断 | 单篇或批量重试 |
| `conflict` | 远端有改动 | 不是数据库里的真实状态，而是写回失败原因的归类，用于页面把这类文章标红 | 人工确认后强制覆盖 |

几个容易混淆的点：

- **`pending_class` 不是错误。** 它表示「AI 没把握」，文章仍然会在语雀待定库里建好档，只是不抽词。你在页面上把它改到正式库后，会立刻触发抽词。
- **`failed` 有多种原因。** 具体原因存在 `documents.error`，直接显示在列表和详情页。常见的是模型调用失败、语雀限流、远端冲突、处理超时。
- **`written` 可以再次写回。** 改完勾选或释义再点写回即可；每次写回都会重新渲染，不会在上次结果上叠加。

## 3. 阶段进度与百分比

`stage` 只用于「当前正在处理」的显示，处理完成后统一置为 `done`，失败置为 `failed`。

| stage | 百分比 | 典型 detail |
|---|---|---|
| `queued` | 5 | 排队中 |
| `classifying` | 20 | AI 分类 |
| `creating` | 35 | 语雀建档 |
| `extracting` | 45 | 抽取候选词 |
| `explaining` | 45 → 95 | 逐词释义，例如 `3/9 路径依赖` |
| `done` | 100 | 待审核 / 待归类 / 已写回 |
| `failed` | 100 | 失败 |

百分比的计算方式是：分类、建档、抽词各占固定值，释义阶段按「已完成词数 / 总词数」在 45% 到 95% 之间线性推进。页面每 1.5 秒请求一次 `/api/progress`，只读数据库，不触发任何处理。

## 4. 批次

`batches` 表记录一次导入动作：

- 扫描收件箱、网页上传各建一个批次，来源记 `inbox`；
- 简悦推送的来源记 `simpread`，并且**复用当前正在跑的那个 simpread 批次**，避免连续推送产生一堆批次；
- 批次内文章严格按入库顺序串行处理，批次之间也是先进先出；
- 当批次内不再有非 `done`/`failed` 的文章时，批次标记为 `finished`。

`total` 按「实际新建成功的文章数」回写，重复文章不会计入。

## 5. 去重

导入时依次判断：

1. 若原文链接（已归一化、去掉追踪参数）已存在，直接返回已有记录，不再新建；
2. 否则比较正文哈希（空白归一化后的 SHA-256 前 16 位），相同则视为重复。

重复文章不会重新建档、不会覆盖你已审核的内容。

## 6. 分类判定

1. 读取 `profiles/*.md`，排除待定库，其余每个库作为候选；
2. 一次请求把「标题 + 正文前 N 字（`classify.body_chars`，默认 3000）+ 全部候选库档案」发给模型；
3. 校验返回：必须覆盖全部候选库、不许出现未知库名、不许重复、分数必须在 0 到 1 之间；
4. 校验失败自动重试一次；仍失败则进待定库并记录原因；
5. 取最高分：低于阈值（默认 0.5）或最高分并列，都进待定库。

全部库的分数与理由存进 `documents.scores_json`，详情页「库打分」折叠面板可查看。

## 7. 建档

- 文档别名为 `kb-` 加正文哈希前 10 位，天然幂等；
- 如果语雀提示别名已存在，程序会查找同名文档并接管，而不是报错；
- 建档后回读正文计算哈希，存为 `yuque_body_hash`，作为下次写回的冲突基线；
- 建档后尝试把文档插入库目录；插入失败只记录提示，不影响后续流程。

## 8. 抽词数量

```
n = clamp(ceil(U / 1000 × density × multiplier), floor, hard_cap)
```

- `U` 是阅读单位数：中文按字、英文按词，**排除代码块、行内代码、图片、HTML 标签和裸链接**；
- `density` 默认 2.5，`floor` 默认 3，`hard_cap` 默认 14；
- `multiplier` 是每个库自己的倍率，可在网页上按库调整。

## 9. 候选词过滤

模型给出 `n + 3` 个候选后，程序会：

1. 检查每个词能否在正文的「可注区域」（普通段落和列表）中精确定位，定位不到直接丢弃；
2. 若长短词互相包含（例如同时选了「机器学习」和「学习」），只保留长词；
3. 按重要度排序后取前 `n` 个；
4. 最终按「首次出现位置」排序展示。

这一步保证了列表里不会出现点了也注不上去的词。

## 10. 释义生成

每个词依次经过：

1. **同库缓存**：查 `glossary` 表里同词同库的记录，命中且非空就直接复用；
2. **在线检索**（`explain.online` 为真时）：并行查询百度百科与 Bing，取标题、摘要和链接；单次请求有超时上限，查询失败不影响后续；
3. **模型综合**：把「词、词所在原句、百科摘要、搜索摘要」交给释义模型，要求结合语境消歧、限制字数、不写套话。

来源标记写进 `terms.sources_json`，页面上以徽章显示，同时区分「命中缓存」。

## 11. 半成品不可见

注释词不是边生成边写库，而是**全部词都生成成功后，在一个事务里一次性写入**，同时把状态置为 `terms_ready`。这样做的原因是：只写一半的话，文章会提前出现在待审核列表里，看起来像是处理完了。

人工手动添加的词不受这个影响，它们直接写入并标记为手动词。

## 12. 人工审核

详情页支持：

- 勾选或取消词条（可全部取消，等于只写原文）；
- 直接修改释义；
- 单条重新生成释义（会绕过缓存）；
- 手动添加正文里已有的词（正文定位不到的词会被拒绝）；
- 修改所属库（见下一节）。

「保存草稿」只写本地数据库；「确认并写回」才会触发写回。

## 13. 改分类

把文章从 A 库改到 B 库时：

1. 在 B 库按同样的别名新建文档；
2. 尝试删除 A 库的旧文档；
3. 更新本地记录指向新文档，清空旧的哈希基线；
4. 若文章此前从未抽词，立即按 B 库的倍率抽词。

删除失败（例如 Token 没有删除权限）不会中断流程，只在页面提示你手动清理旧文档。

## 14. 写回与冲突

写回前先读取远端文档：

| 情况 | 处理 |
|---|---|
| 远端格式不是 Markdown（例如你在语雀网页端用富文本改过） | 暂停，提示「已转为 lake 格式，确认后可强制覆盖」 |
| 远端正文哈希与本地上次写入时记录的不一致 | 暂停，提示「远端正文已被修改，确认后可强制覆盖」 |
| 正常 | 直接写入 |

强制覆盖会跳过以上两项检查，用本地原文和当前勾选重新渲染后整篇替换远端。**远端的手工修改会丢失**，所以这个动作只在你确认后才执行。

写回成功后：

- 回读远端正文，更新哈希基线；
- 状态置为 `written`，清空错误；
- 把本次用到的释义写入同库缓存，下次同词直接复用；
- 兜底检查文档是否在目录里，不在就插到顶部。

## 15. 写回队列

写回不是同步执行，而是进入内存队列由单独的后台协程串行处理：

- 队列条目同时持久化到 `pending_writes` 表，**服务重启后会自动恢复未完成的写回**；
- `force` 标记只能升级不能降级，避免后到的普通提交把强制覆盖的意图冲掉；
- 失败会累加尝试次数，同一个作业累计 3 次失败后移出队列，避免无限重试；
- 后台失败会把文章状态置为 `failed` 并写入原因，页面据此显示冲突提示。

因为写回是异步的，点击按钮后页面会立刻跳转，实际结果稍后在列表或详情页体现。

## 16. 超时与重启恢复

- 导入时写入 `deadline_at`（默认 10 分钟）。停留在 `imported`/`classified`/`created` 且已过期的文章会被标记为失败，提示「处理超时」，避免永远卡在中间态。
- 服务启动时会把上次中断在中间态的任务标记为失败，并收口对应批次，而不是让它们看起来还在运行。

## 17. 保留状态

与处理状态完全独立：

| 值 | 含义 | 影响 |
|---|---|---|
| `active` | 进行中 | 默认视图显示 |
| `archived` | 已归档 | 只在「已归档」视图显示 |
| `trash` | 回收站 | 只在「回收站」视图显示 |

永久删除只能作用于回收站里的文章，且**只删本地记录**（连带词条、事件），不会删除语雀上已存在的文档。这是刻意的：把「本地清理」和「远端删除」分开，避免误删知识库。

若开启 `retention.auto_archive_written`，写回成功后会自动归档本地记录。

## 18. 事件日志

`events` 表记录每个关键动作：导入、分类、建档、抽词完成、写回、改分类、备份、错误等。排错时按文档 ID 查这张表，能看到完整的动作序列和对应载荷。
