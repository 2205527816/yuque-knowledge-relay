# 技术实现

本文说明代码分层、数据表、关键算法与设计取舍。想改代码或排查疑难问题时看这里。

## 1. 技术选型

| 项目 | 选择 | 原因 |
|---|---|---|
| 语言 | Go 1.27 | 单文件编译、部署简单、并发模型适合后台队列 |
| 数据库 | SQLite（`modernc.org/sqlite`，纯 Go 实现） | 无需额外进程、免 CGO，方便交叉编译和本机部署 |
| 模板 | 标准库 `html/template` | 不引入前端构建链，改完刷新即可 |
| AI | 任意 OpenAI 兼容接口 | 分类与释义各配一个模型，不强绑某个厂商 |
| 网页解析 | `goquery` + `html-to-markdown` | 处理简悦导出的 HTML |
| Markdown 渲染预览 | `goldmark` | 审核页左侧预览 |
| HTML 清洗 | `bluemonday` | 渲染不可信 HTML 时防注入 |
| 图片处理 | 标准库 `image` + `golang.org/x/image` | 队列缩略图与图片本地化 |

`CGO_ENABLED=0` 即可编译成静态单文件，目标机器装不装 Go、有没有 glibc 都不影响运行。

## 2. 代码分层

单一 `main` 包，按职责分文件：

```
入口与路由    main.go
配置          config.go
数据库        db.go（建表/补列）  store.go（查询与领域对象）
导入解析      ingest.go
分类          classify.go
抽词          terms.go  limits.go
释义          explain.go
排版渲染      render.go
流程编排      pipeline.go（建档/写回）  pipeline_ai.go（分类/抽词/重试）
队列          writequeue.go（写回）  routes_post.go（批次）
HTTP 处理器   handlers*.go  routes_post.go
语雀客户端    yuque.go  yuque_chain.go  yuquewb.go
备份与图片    backup.go  imagelocalize.go  imgproxy.go
```

几个刻意的设计：

- **纯函数与副作用分离。** 打分校验、候选词过滤、排版渲染都是无状态函数，测试不需要数据库和网络。
- **外部依赖可替换。** `clientsFor` 是变量，测试时替换成语雀桩；图片下载、模型调用同样留有可替换入口。
- **渲染永远从原文开始。** `renderMarkdown` 只接受原始正文和词表，不在上次结果上叠加，保证多次写回结果一致。

## 3. 数据表

### `libraries`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `name` | 库名，唯一，同时是档案文件名 |
| `yuque_namespace` / `yuque_slug` | 对应语雀库路径 |
| `multiplier` | 候选词倍率，0.5–2.0 |
| `profile_path` | 档案路径 |
| `profile_version` | 档案版本，保存一次加一 |

### `documents`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `source_url` | 归一化后的原文链接 |
| `title` / `author` / `published_at` | 元信息 |
| `raw_md` | 原始正文（Markdown），渲染的唯一来源 |
| `content_hash` | 正文哈希，唯一，用于去重 |
| `units` | 阅读单位 U |
| `status` | 处理状态 |
| `library_id` | 所属库 |
| `scores_json` | 各库分数与理由 |
| `yuque_doc_id` | 语雀文档 ID，唯一 |
| `yuque_body_hash` | 上次写入后远端正文哈希，冲突检测基线 |
| `error` | 最近一次错误说明 |
| `retention_status` / `archived_at` / `deleted_at` | 保留状态 |
| `deadline_at` | 处理超时时间 |
| `batch_id` | 所属批次 |
| `stage` / `stage_pct` / `stage_detail` | 细粒度进度 |

### `terms`

| 字段 | 说明 |
|---|---|
| `document_id` + `term` | 联合唯一 |
| `type` / `importance` | 模型给出的类别与重要度 |
| `para_index` | 首次可注段落序号，用于排序 |
| `explanation` | 释义文本 |
| `sources_json` | 释义来源（百科、搜索、是否缓存） |
| `selected` | 是否勾选，默认 1 |
| `manual` | 是否为人工添加 |

### `glossary`

同词同库的释义缓存，唯一键 `(term, library_id)`。写回成功时同步，重新生成时可绕过。

### `events`

动作流水，`type` 如 `imported`、`classified`、`created`、`terms_generated`、`written_to_yuque`、`library_changed`、`error`。排错先看这张表。

### `batches`

一次导入动作的汇总，`total` 是实际新建的文章数。

### `pending_writes`

写回作业的持久化副本：

| 字段 | 说明 |
|---|---|
| `document_id` | 主键，一篇文章同时只有一个待写回作业 |
| `force` | 是否强制覆盖，只能由 0 升到 1 |
| `attempts` | 失败次数，达到 3 次后作业被移除 |

### `settings`

预留的键值表，用于存放运行期可调参数。

### 建表与迁移

启动时执行 `CREATE TABLE IF NOT EXISTS`，随后检查 `documents` 是否缺少后来新增的列（批次、阶段、保留状态等），缺哪列补哪列。老版本数据库可以直接升级，不需要手动改表。

## 4. 导入解析

`parseFile` 支持 Markdown 与 HTML：

1. 读取文件，若是 HTML（`<!doctype` 或 `<html` 开头）则转换成 Markdown；
2. 解析 YAML Front Matter，取标题、原文链接、作者、发布时间；
3. 标题优先级：Front Matter → HTML `<title>` → 正文首个一级标题 → 文件名；
4. 若正文第一行是与标题相同的 H1，剥离该行，避免语雀出现重复标题；
5. 原文链接归一化：去掉 `utm_*`、`spm`、`from`、`share_token` 等追踪参数和末尾斜杠；
6. 计算正文哈希与阅读单位 U。

### 阅读单位 U

先剥离围栏代码块、行内代码、图片语法、HTML 标签和裸链接，保留普通链接的锚文本，然后：

```
U = 中文字符数 + 英文单词数
```

这个值同时决定注释词数量和进度展示，排除代码可以避免技术文章被算出过大的字数。

## 5. 分类

`loadProfiles` 扫描 `profiles/*.md`，文件名即库名。

一次请求同时给出全部候选库档案，让模型横向比较。这样做的代价是提示词较长，好处是分数之间可比，能直接看出「两个库都在抢这篇文章」。

校验（`parseScores`）比一般实现更严格：

- 缺库、未知库名、重复库名、分数越界，全部视为无效；
- 无效就重试一次，两次都无效才降级为待定。降级时会把原因写进文章记录，而不是静默塞进待定库。

选库（`pickLibrary`）只看最高分，且**必须唯一**。并列最高一律进待定，避免随机选择破坏可预期性。

## 6. 抽词

调用一次模型，要求给出 `n + 3` 个候选（预留过滤余量），每个候选包含词、类别、重要度、所在原句。

`selectCandidates` 做三件事：

1. **可注性检查**：用与渲染器同一套逻辑判断该词能否在「普通段落 / 列表」中定位；
2. **长词优先**：若短词被已保留的长词包含，丢弃短词；
3. **排序**：先按重要度取前 `n` 个，再按首次出现段落排序展示。

使用与渲染器相同的定位函数，是为了避免「列表里有这个词，但点了注不上去」这种不一致。

## 7. 释义

`explainOne` 的优先级：

1. `glossary` 命中且非空 → 直接复用，标记「缓存」；
2. `explain.online` 为真 → 并行查百度百科与 Bing，各自有超时上限；
3. 把词、原句、检索摘要交给模型综合成稿。

模型被要求：

- 结合原句语境消歧，多义词用「此处指……」限定；
- 单段、不含换行（便于放进单行引用块）；
- 不出现「根据维基百科」这类套话，不带角标。

任一外部源失败都不会中断，最差情况退化为纯模型生成，并在来源里标记 `llm_fallback`。

## 8. 排版硬规则

`renderMarkdown` 是纯函数，核心规则：

1. 被勾选的词在正文中用 `***词***` 标记；
2. 该词所在段落之后紧跟引用块 `> 词：释义`；
3. 同段多个词合并在一个引用块内，用空引用行 `>` 分隔，顺序按段内首次出现位置；
4. 每个词**全文只标一次**，在首次可注位置；
5. 词与段落之间、段落与后续内容之间保持一个空行，不产生连续空行；
6. 除标注和追加引用外，原文一字不改。

跳过区域：

- 块级：标题、围栏代码块、表格、已有引用块、HTML 块、水平分割线；
- 行内：行内代码、链接整体、图片、尖括号自动链接、HTML 标签、已有粗体/斜体/删除线。

英文与数字词按词边界匹配（勾 `AI` 不会命中 `main` 里的 `AI`）；中文按最长子串优先。

未能命中的词会作为 `missing` 返回，页面提示「未命中」但不阻断写回。

### 出处行

若原文链接有效且正文里还没有出处行，渲染时会在正文开头插入一行：

```
> 本文由 [简悦 SimpRead](https://simpread.pro) 转码，原文地址 [example.com](https://example.com/...)
```

已存在同样格式的出处行则跳过，保证重复渲染不会叠加。

## 9. 写回与冲突

```
读取文档 → 缺文档先建档 → 渲染 → 读远端 → 冲突检查 → 写远端 → 回读 → 记账
```

冲突检查有两个维度：

1. 远端 `format` 不是 `markdown`：说明被富文本编辑器改写；
2. 远端正文哈希与 `yuque_body_hash` 不一致：说明上次写回后又被改过。

两者都可通过 `force` 跳过。跳过时用本地原文整篇替换，远端手改内容会丢失——这是有意的取舍：与其做三方合并（Markdown 结构差异下几乎不可靠），不如让用户明确选择。

写回成功后回读远端正文计算哈希作为新基线，并同步 glossary、兜底加入目录。

## 10. 队列与并发

两套后台队列，都是单工：

- **批次队列**：批次之间 FIFO，批次内也严格串行。SQLite 写入不适合并发，串行也保证同一篇文章不会同时被两个流程改。
- **写回队列**：独立于批次，避免「写回一篇卡住整个导入」。

队列状态持久化在 `pending_writes`，重启后恢复。写回入口与恢复逻辑共用同一段代码，所以恢复的作业和手动提交的作业行为一致。

交互上还有一个细节：写回是异步的，页面点击后立即跳转，因此前端通过 `/api/progress` 的 `writes` 字段判断是否还有写回在进行，完成后才提示「全部处理完」。

## 11. 前端

没有打包构建，也没有前端框架：

- 服务端渲染模板，页面切换用普通导航；
- 详情页预览用 `fetch` 提交表单，拿到 HTML 片段替换局部区域；
- 进度轮询是单例定时器，元素每帧重新查询，避免重复绑定；
- 审核页双栏支持拖动调整高度与宽度、单栏收起后从边缘恢复，窄屏自动改为上下排列；
- 图标用 SVG `symbol` 引用，字体使用本地 Noto Sans SC，不依赖外部 CDN。

## 13. 已知限制

- **无鉴权**：服务本身不做登录校验，必须靠前置代理保护。
- **单用户**：数据库与文件布局按单实例设计，没有多租户隔离。
- **同步写入远端**：写回是整篇替换，不做增量合并。
- **模型依赖**：分类与抽词质量直接取决于所配模型；不同模型需要重新校准阈值。
- **信源覆盖**：释义联网检索固定使用百度百科与 Bing，其他信源需要改 `explain.go`。
